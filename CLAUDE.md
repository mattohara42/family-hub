# Family Hub — Claude Context File

*Read at the start of every session. This file is intentionally lean — it loads on every turn. Detailed reference (file-structure maps, per-feature function/state/anchor inventories, data shapes, API constants) lives in `FEATURES.md`; read that on demand.*

---

## What This Project Is

A four-file family dashboard: three files plus `hub-theme.css` for its theme tokens. No build step, no npm, no framework — CDN scripts only (Firebase 9 compat, Google Identity Services).

| File | Contents |
|---|---|
| `family-hub.html` | HTML structure + CDN script tags (no inline CSS/JS) |
| `hub-theme.css`   | Theme tokens only: fonts, Colors palettes, each Theme's material tokens, data colors. Loads first; other apps may copy it unchanged |
| `family-hub.css`  | Every rule that reads them: layout, components, theme structure |
| `family-hub.js`   | All JS logic + config block at top |

These files must sit in the same directory, alongside `config.js` (Firebase config + Google client ID as `window.FH_CONFIG`, loaded before `family-hub.js`). On Netlify, `netlify-build.js` rewrites `config.js` from the `GOOGLE_CLIENT_ID`/`FIREBASE_CONFIG` env vars when both are set, so a fork runs its own projects without editing tracked files; don't move those values back into `family-hub.js`. Serve via Netlify (prod) or `python3 -m http.server 8080` → `http://localhost:8080/family-hub.html`.

Shared state (shopping, todo, budget) lives in Firebase Firestore. Photos are blobs in IndexedDB. Everything else is `let` globals + `localStorage` (`fh_*` keys).

## Architecture Invariants (don't break these)

- **No build tooling.** Any library must be a CDN `<script>`/`<link>` and respect the CSP in `family-hub.html` (`img-src` includes `'self'`).
- **`pond/` is vendored, not ours to edit.** The Pond Chimes screensaver mode is a **git subtree** of `mattohara42/pond-chimes`, kept byte-identical so upstream work comes back with `git subtree pull --prefix=pond https://github.com/mattohara42/pond-chimes main --squash`. It runs in a same-origin iframe; anything the hub needs from it (audio, hiding its title card) is reached in from `family-hub.js` — never by editing files under `pond/`. Framing it requires CSP `frame-src 'self'` **and** `X-Frame-Options = "SAMEORIGIN"` in `netlify.toml`. (FEATURES.md §19)
- **Full-viewport flex.** `body` is `flex-column 100dvh`. `min-height: 0` is required at every flex level to allow shrinking below content size. `.sidebar > *` must keep `flex-shrink: 0` — or cards compress instead of the sidebar scrolling.
- **Layouts are grouped by view shape.** Month/Week are grids that need the full width; Day/Agenda are single-column lists. A widget placed `'beside'` sits in `#besideStrip` next to the events only in Day/Agenda (desktop, wider than 860px, not portrait: `besideColumnActive()`) and falls back to the sidebar in Month/Week. `syncBesidePlacement()` moves cards only when that gate flips, so a new view must be added to that check, and anything that changes the gate's inputs must call it. The column's width is `--sidebar-w` on `.layout`; set sidebar width through that variable, not a literal `grid-template-columns`. (FEATURES.md §6)
- **Google OAuth = GIS token client** (not code flow). Token is in-memory only (`let googleToken`), never localStorage. `file://` blocks OAuth — must serve from `localhost` or HTTPS. Any new serving origin must be added to Google Cloud Console (Authorized JS Origins) **and** Firebase Console (Authorized Domains). `generative-language` is **not** a valid OAuth scope.
- **Touch tap-target CSS must stay inside `@media (hover: none)`** — larger button/list padding rules must never leak outside that block.
- **Mobile has no bottom nav — Calendar is the permanent surface.** "Mobile" (and every "under 640px" below) means narrower than 640px **or** a phone turned sideways: `(max-height: 500px) and (orientation: landscape) and (pointer: coarse)`. Each mobile CSS block repeats that full query and `updateIsMobile()` mirrors it, so change them together. Sideways only, a short-height block also hides `#yearStrip` and lets the Month grid scroll at a 64px minimum row height. Under 640px the `.sidebar` is unconditionally hidden; nothing in it besides Shopping/To-Do/Home Assistant/Assistant is mobile-reachable (same as before this redesign — Chores, Word of the Day, etc. have never had mobile UI). Budget is a narrow exception: it still has no sidebar card or Settings tab on mobile, but `#calBudgetPrivacyBtn` (bordered like the 🏠 and ⚙️ header buttons) in the calendar header (beside the 🏠 Lists icon in `.cal-title-zone`) surfaces the same per-device `budgetHidden` gate as the desktop-only Budget card's own 👁 button (`toggleBudgetPrivacy()`/`applyBudgetPrivacy()`), shown only when `isMobile && budgetItems.length` and kept in sync when crossing the breakpoint (`applyBudgetPrivacy()` in the `resize` listener) — added because the bill-amount pills it gates (Month's `.cal-event-budget`, Day's "Bills Due Today" section, Agenda's `.agenda-bill` rows) otherwise had no mobile control at all. One floating button replaces the old tab bar — `#mobileAddFab` (`openNewEventFromFab()`, quick-add defaulting to the viewed day in Day view, today otherwise; hidden while the event editor is open via `body.evt-editor-open`) — and the Lists sheet opens from the 🏠 app icon (`.cal-app-emoji`) in the header instead of its own floating button; that icon is a real `<button onclick="openMobileLists()">` now (was a decorative `<em>`), reset to its old borderless look on desktop and given a visible border/background under 640px so it reads as tappable. `openMobileLists()` no-ops when `!isMobile`, since the sheet's CSS only exists under that query. The icon still carries the existing 7-tap fireworks Easter egg (`setupEmojiFireworks()`) — unrelated, don't conflate the two handlers. The sheet holds Shopping/To-Do/Home Assistant/Assistant as sections — `MOBILE_SHEET_SECTIONS` in `family-hub.js` maps each widget key to its section wrapper id, and `applyWidgetPlacement()` reparents the real card into it when `isMobile` (no duplicated markup); `setMobileListsSection()` toggles which one shows, not persisted (always opens on Shopping). Each reparented card's own `<h2>` is hidden inside the sheet (`.mobile-sheet-body .card-header h2`) since the active tab already names the list; the header row's action buttons (SMS, refresh, clear-done/-all) stay and right-align (`justify-content: flex-end`) now that they're the row's only child — a new sheet section's card needs the same shape (title in `h2`, actions in a sibling wrapper) to lose its title for free. One more header-row thing is mobile-sheet-only cleanup, not a removed feature: `initWidgetDragDrop()`'s `.widget-drag-handle` (⠿) is hidden there since a card's sheet position is fixed by `MOBILE_SHEET_SECTIONS`, not draggable. (📱 SMS, `#smsTriggerBtn`, is icon-only everywhere and sits in the Shopping add row, not the header; `sendToContact()`'s `sms:` link still opens the phone's own Messages app.) The Home Assistant and Assistant tabs are each hidden unless their widget is toggled on (`applyWidgetVisibility()`), bouncing back to Shopping if the open section gets disabled out from under it. Find Events (💡) is an icon-only button at the end of the sheet's tab row instead of its own chrome. The sheet's grab handle is live (`setupMobileSheetDrag()`: drag down closes, drag up or tap expands to 92svh), and the sheet uses `--surface-solid`, not the translucent `--surface`. Settings is not in the sheet at all — it's `#calSettingsBtn` (`.cal-header-settings-btn`), a standalone header nav item pinned to the top-right corner of row 1 (hidden by default so it drops out of the desktop 3-column grid; the mobile query turns it on), mirroring the desktop-only sidebar control card's own ⚙️ button. Widget *placement* ('bottom'/'beside') is still desktop-only; the screensaver never runs under 640px. Tapping a Month cell on mobile opens that day in Day view (`onMonthDayTap()`), and so does tapping its bill/to-do pills (`monthInfoPillClick()`, inert on desktop); desktop keeps tap-to-create. The header is one row: the view toggle becomes a Month/Day/Agenda/Week `<select id="calViewSelect">` beside ⚙️ (`switchCalView()` keeps it in sync; Week was meant to be desktop-only via a `hidden` option, but iOS lists hidden options anyway and it got used, so it was made official 2026-10-22; on a phone its days stack as rows so a swipe pages it like the other views) and the prev/next arrows are hidden — both redundant with `setupCalSwipe()`, which follows the finger and lands the period change as a slide (`slideCalPeriod()`; FEATURES.md §Swipe / period slide). The four view containers live inside a `#calViews` wrapper — it's the drag target and the positioning context for the outgoing-period ghost, so don't reparent them out of it. Preferences itself is filtered on mobile too: `SETTINGS_GROUPS` items can carry `desktopOnly: true` (screensaver, Mowing, Widget Layout, Weather, Feeds, Chores — each either a desktop-only concept or a widget with no mobile surface), and `renderSettingsNav()` drops those under `isMobile`. Assistant's settings tab is *not* desktopOnly — its Gemini API key needs setting from a phone too, same reasoning as Home Assistant's token. The mobile type scale (`--text-*` tokens, plus a `#settingsModal` text/line-height bump) is intentionally larger than desktop's — sized for a wall panel read from a few feet away, not a phone in the hand.
- **Day/Agenda typography is token-driven, not ad hoc.** `--fs-title`/`--fs-item`/`--fs-meta` (hub-theme.css `:root`) are semantic aliases into the `--text-*` ladder — use them for new Day/Agenda markup instead of a literal `font-size`. Currency and clock-time text gets `font-variant-numeric: tabular-nums`. The display face (`--font-display`: Fraunces in Tactile, Inter Tight in Glass, Newsreader in Paper) only renders on `h1/h2/.cal-app-title`, the screensaver clock and a few "prominent numeral" classes (`.budget-day-amt`, `.wx-temp`, `.countdown-days`, …); body text is `--font-body`. Card titles (`.card-header h2`) are `--font-body` too, at semi weight: the display serif read as blocky at that size (2026-11-07). The display face anywhere else is a scoping bug, not expected behavior. Chrome icons (card titles, toolbar buttons, Settings nav and panel labels, modal titles and tabs, action buttons) are Lucide SVGs from the inline sprite at the top of `family-hub.html`, drawn with `icon('name')` (or `icon('name', true)` when a text label follows) in JS or `<svg class="ic"><use href="#i-name"/></svg>` in markup (FEATURES.md §5, Icons); content emoji (Easter eggs, user-picked countdown/app icons and the emoji-picker buttons, weather art, toasts, calendar names, emoji inside sentences) stay emoji. `<select>` options can't hold an SVG, so they carry plain text, no emoji, and ✕/↻/↗ are typographic marks, not emoji.
- **Agenda, Month, Day and Week share one event color treatment.** A solid fill of the event's own calendar color with white text: `.cal-event`, `.day-event-pill` and `.week-event` set `background: ev.color` inline; `.agenda-event` reads `--event-color` (set inline from `ev.color`, fallback `--event-fallback`) as its `background`. Agenda used to be a 32% tint over `--surface-solid` with theme text, which read as a different style from the other two views and was changed to match (2026-09-25). Don't reintroduce a fill that ignores `ev.color`, or a per-view treatment: the same event should read the same in every view. Text color comes from `readableTextOn(ev.color)` (white unless white would fall under 3:1 on that fill, i.e. luminance above 0.30; then dark, which catches mid-tones like Okabe-Ito orange as well as Banana/Citron), and `paintEventFill(el, color)` sets fill + text for Month pills/bars and Day/Week pills; Agenda sets `--event-color` plus the same text color. Both route the color through `eventFill()` first, which is a no-op except under the per-device Wall display setting (`wallDisplay`), where it darkens the fill (same hue) until white clears that 3:1 bar, so a wall panel never shows near-black event text; new event render paths must go through `paintEventFill()`/`eventFill()` too. A missing color falls back to `var(--event-fallback)` instead of no fill (which once left white text on a white cell). That token lives in `hub-theme.css` and darkens `--muted` in dark and Accessible colors, because `--muted` is tuned as gray text and some looks make it too pale for white text; `npm test` checks white on it at 3:1 in every look, so don't point the fallback back at `--muted`. On mobile Month, pill/bar text also drops emoji (`stripEmoji()`): a leading 🗑️/🎉 wrapped onto its own line in a few-character cell. All of them share one depth treatment too (`/* ── Event depth ── */` in family-hub.css: a faint bezel plus a soft drop shadow, chosen 2026-10-22 because the fills read as flat). Never set an inline `box-shadow` on an event element, since it would wipe that out. Mobile Month's member stripes go in the `--member-stripes` variable, which the depth rule layers on top.
- **Colors axis (the Settings "Colors" picker; code calls it `appMode`):** `'auto'` (true default — follows the device's `prefers-color-scheme`, resolving to `'light'`/`'dark'` via `resolveAppMode()`), plus manual `'light'`, `'dark'`, `'colorblind'`. `applyAppMode()` swaps body classes off the *resolved* mode (dark = no class) while `appMode` itself keeps `'auto'` as the logical value; a `prefers-color-scheme` `change` listener reapplies whenever `appMode === 'auto'`. A per-device toggle (`autoThemeBySun`, `fh_autoThemeSun`) makes Auto follow sunset/sunrise from the first weather location instead, for screens whose OS never goes dark (the Pi panel). Nautical and Aurora were removed 2026-11-07; a saved `fh_mode` of either (or the older `'amazing'`/`'nautical-light'`) is cleared on load, so that device falls back to Auto.
- **Theme axis (material), orthogonal to Colors.** Settings → Look & Feel has two pickers: **Theme** (`'tactile'` default, `'glass'`, `'paper'`; registry `THEMES` in `family-hub.js`, per-device `fh_theme`, `applyTheme()` toggles `body.theme-<id>`; Tactile = no class) and **Colors** (the light/dark/accessible axis below). Component CSS reads **material tokens** declared on `body` (not `:root`, since they reference theme colors): `--card-bg/-border/-shadow/-blur`, `--cal-card-bg/-blur`, `--grain-opacity/-blend`, `--display-weight`, `--control-*` and `--tab-radius` (view tabs, period arrows, forecast toggle, `.btn`), `--well-bg/-shadow` (hourly tiles, mini-months), `--col-bg/-border/-radius/-gap/-blur` (Week columns, Month cells), `--today-bg/-ring`, `--week-bg`, `--event-radius`, `--chip-radius`, `--modal-bg/-border/-shadow/-blur` and `--modal-scrim/-scrim-blur` (every `.modal` and its `.modal-overlay`; modals stay fully opaque in every theme, Glass included: the wall panel's Chromium draws no `backdrop-filter`, so an 80% "frosted" Glass modal let the calendar's text read straight through; no modal has its own tilt or accent glow since 2026-11-07). `--scrim` without the prefix is a different, older token: the background photo's tint, set per palette on `:root`. A body-level token by that name overrode it and darkened every photo. Tactile's values are the defaults (plus a `body.light-mode` set); a theme is one `body.theme-x` block (plus `body.theme-x.light-mode`) in `hub-theme.css`, which holds the tokens in cascade order and loads before `family-hub.css` (three late overrides stay at the end of family-hub.css because they must load later: the wall-display type ladder, the phone `:root` ladder and Glass's phone `--col-radius`); only a few structural rules tokens can't express (Glass's `--scene` background and transparent calendar card, Paper's ruled day dividers) stay in family-hub.css's `✦ THEMES` section. Other apps may copy `hub-theme.css` and `tools/theme-check.js` unchanged, always as a pair (the checker's shared checks name tokens the file must define, such as `--event-fallback`), so keep the file tokens-only (custom properties and `@font-face`; the test lints it). One app does today: **Fudget** (`mattohara42/fudget`, the family budgeting app), which copies both files and `fonts/` from a merged Hub commit with `node tools/sync-hub-theme.js <hub checkout>` and pins them in `hub-theme.lock.json`. Its `--check` is stricter than our `npm test`, so a token change that passes here can still fail there: it checks Fudget's own `--app-*` tokens against our surfaces, requires `--status-ok/-watch/-over` to stay green, amber and red, and its lint only accepts the body classes the Hub uses now (`light-mode`, `colorblind-mode`, `safe-palette-on`, `has-bg`, `theme-glass`, `theme-paper`). After changing a token, the fonts or a theme class, sync Fudget and run its `--check`, and treat renaming a body class or adding a Theme as a change to both apps. `tests/theme-contrast.test.js` checks every look, each theme in dark, light and Accessible, derived from the CSS (text 4.5:1, bars/focus/charts 3:1), so run `npm test` after touching a token, and when it fails nudge the named token by the smallest step that passes. Its data colors (`--status-ok/-watch/-over`, `--status-ink`, `--track`, `--link`, `--focus`, `--chart`) are built from the palette through `--status-*-keep`/`--link-keep` mixes toward `--text`, so a palette change carries through; nothing in the Hub reads them yet, but Fudget does, so they aren't dead code. **Style new components with these tokens, never a literal surface/radius/shadow or a per-theme selector**: that's how Tactile ended up with half the UI still in the old Basic look. `body.has-bg` (photo) and KTD-4 (`colorblind-mode`/`safe-palette-on`: no grain, no accent glow) also set tokens, and the theme blocks come after them so a theme's surfaces win. Paper may retune the palette under light/dark but leaves `colorblind-mode`'s alone (`:not(.colorblind-mode)`). The one exception is Glass's Accessible gray (`body.theme-glass.colorblind-mode`): Accessible's own gray fails on clear glass, so don't "fix" it back. Fonts are self-hosted in `fonts/` (CSP is `'self'`): Fraunces/Hanken (Tactile, pre-cached by `sw.js`), Inter Tight (Glass), Newsreader/IBM Plex Sans (Paper, runtime-cached). Themes set color tokens (`--surface-solid/-hi/-lo`, `--ink`, `--line`, `--accent`…) and component CSS reads those, never a literal hex or `rgba()` of a token's value; translucent tints use `color-mix(in srgb, var(--token) N%, transparent)`. The material rules are `body .card`-style (one element + classes), so an older per-mode rule like `body.light-mode .x` outranks them; when one fights the material, delete the old rule rather than raising specificity.

## Known Gotchas

| Gotcha | Detail |
|---|---|
| `file://` blocks OAuth | Use `http://localhost:8080` or deploy to Netlify (HTTPS) |
| GIS token expires (~1h) | Access token is in-memory and short-lived; on an all-day wall display it silently lapses, so a later calendar write 401s and reads as a hang/"timeout." `tokenExpiresAt` tracks TTL from `resp.expires_in`; `scheduleTokenRefresh()` does a silent `prompt:''` refresh ~5 min early; `ensureFreshToken()` awaits a valid token and `calFetch()` wraps Google API writes (refresh-first, one 401 retry, 20s AbortController timeout). Route new calendar writes through `calFetch`, not raw `fetch` + `Bearer ${googleToken}` |
| Quiet sign-in needs pop-ups allowed | `requestAccessToken({ prompt: '' })` on load (session restore) and in `scheduleTokenRefresh()` still opens a GIS pop-up, and browsers block pop-ups a page opens before any tap. On the wall panel that meant re-tapping Sign in after every reboot; a Chromium `PopupsAllowedForUrls` policy fixed it (setup step 10, item 2) |
| New serving origin breaks OAuth | Add to Google Cloud Console → Authorized JS Origins AND Firebase → Authorized Domains |
| Photos Picker 403 | Must include `Authorization: Bearer ${googleToken}` header when downloading images |
| Pond screensaver taps don't reach the hub | Pointer events inside the `#saverPond` iframe never hit the hub's `window` listeners, so wake is wired into the iframe document by `wireSaverPondWake()`. In `'play'` mode that's a keypress or the `#saverWakeBtn` corner button only — waking on `pointermove` would make the pond unplayable with a mouse |
| Pond audio needs the parent | The pond only calls `initAudio()` on its own tap, so as a screensaver it would be silent; `applySaverPondSound()` starts and mutes it from the hub via the same-origin `contentWindow`. On the wall panel Chromium blocked it after a reboot (nobody had tapped yet) until the launch line got `--autoplay-policy=no-user-gesture-required` (setup step 10c). Elsewhere a blocked start can't be retried by a tap yet (SCREENSAVER_BACKLOG.md) |
| Gemini free tier disabled | Happens when GCP billing is enabled — use an AI Studio key from a billing-free project |
| Gemini model deprecated | Update `GEMINI_MODEL` in `family-hub.js` **and** `DEFAULT_MODEL` in `netlify/functions/ai.js` together; watch for `404 NOT_FOUND`. The proxy rejects any other model with a 400 naming `DEFAULT_MODEL`, so a one-sided update fails loudly. The Assistant's voice is a separate model with the same pairing: `GEMINI_TTS_MODEL` in `family-hub.js` and `TTS_MODELS` in `ai.js` (Interactions API, not `generateContent`); if it breaks, replies fall back to the device voice rather than going silent |
| `calEventCache` only holds the period on screen | `loadAllCalendars()` resets it and fetches just the current view's range (one day in Day view, one month in Month view; ICS subs are the exception, expanded over months). Anything that needs "the next N days" regardless of view must fetch its own range, as the Assistant does with `refreshAssistantCalendar()`, or it silently sees one day |
| Gemini key lives on Netlify, not the device | Production leaves `mealAiKey` blank so `geminiFetch()` uses `/.netlify/functions/ai` (`GEMINI_KEY`). Don't reintroduce `if (!mealAiKey) return` gates: they made every device need its own pasted key. The function only answers same-origin requests (`Origin` host must equal `Host`), which stops casual reuse of the URL but not a forged header |
| `generative-language` OAuth scope | Doesn't exist — `invalid_scope`. API key only for Gemini |
| Weather is keyless | Widget uses **Open-Meteo** (forecast/geocode/AQI) + **RainViewer** (radar) + **NWS** (US alerts) — no key, no signup. `loadWeatherByCity()` geocodes then fetches. Note: `netlify/functions/events.js` (event discovery) still uses an OWM key — separate feature |
| Open-Meteo uses WMO codes | Conditions are integer WMO codes, not strings. `wmoToCondition()` maps them to the OWM-style strings (`Clear`/`Rain`/…) the renderer keys on |
| Open-Meteo times are location-local | ISO strings have no zone suffix (`timezone=auto`); use `omEpoch(iso, utc_offset_seconds)` to get a real UTC epoch |
| Phone override silently does nothing | A media query adds no specificity, so a phone rule loses to any equal-specificity base rule that comes later in `family-hub.css`. The generic phone blocks live at the very end of the file ("Phone overrides (generic)") for this reason; put new phone tweaks there or anywhere after the base rule they target. Modal padding, the small-phone month label and the Month label's min-width were all dead this way until 2026-10-21 |
| Theme-color alias tokens go on `body` | Themes set `--text`/`--muted` (and friends) on `body.*-mode`, and a `var()` in a custom property resolves where it's declared. So an alias like `--ink: var(--text)` on `:root` froze to the dark theme's value and gave light mode near-white text (the on-screen keyboard hit it). `--ink`/`--ink-soft` now sit in a `body` rule; a new alias of a theme color belongs there too. `--fs-*` → `--text-*` is fine on `:root` because the type ladder is redefined on `<html>` |
| Page text isn't selectable | `body` sets `user-select: none` (a finger dragged across the wall panel kept selecting text); only `input`, `textarea` and `[contenteditable]` opt back in. A new place where text must be copyable needs its own `user-select: text` |
| Touch tap-target CSS leak | Larger button/list padding MUST be inside `@media (hover: none)` |
| Hover color sticks after a tap | A tap leaves `:hover` on the tapped element, and the wall panel has a mouse attached, so it reports `(hover: hover)` and the `@media (hover: none)` resets never apply there (the › arrow stayed blue). A `pointerdown` listener sets `html.touch-input` from the last pointer type; hover rules that change background/border/transform are written `html:not(.touch-input) .x:hover`. Gate new ones the same way |
| iOS page bounce despite `overflow: hidden` | `body`'s `overflow: hidden` alone doesn't stop iOS Safari's elastic rubber-band/pan on the document: that bounce is tied to the root scroller, not to whether it actually overflows. `html` (which had no rules at all before this) and `body` both need `overscroll-behavior: none` to pin the page down. This is global, not modal-specific, and does NOT reach into a real scrollable descendant's own local bounce: WebKit applies elastic rubber-band per scrollable element, independent of the document root, so a genuinely scrollable box (`#eventEditorModal .modal`, `.sidebar`, `#weekView`, …) needs its own `overscroll-behavior` too if it should feel pinned while its content scrolls. Confirmed on-device (both iOS Safari and Chrome, same WebKit engine) that the html/body fix alone wasn't enough for `#eventEditorModal .modal` specifically |
| Calendar swipe ghost falls back into flow | The outgoing period is a clone pinned over `#calViews` with `position: absolute`, but `.cal-grid` also sets `position` (relative, for its multi-day overlay) and wins on source order at equal specificity. The rule is `.cal-views > .cal-view-ghost` for that reason — flatten it to a bare class and the ghost becomes a second in-flow child, halving both panes' height and stacking them vertically mid-slide |
| `preventDefault()` on `touchstart` kills taps | Cancelling `touchstart` suppresses the click the browser would synthesize from that touch. `setupWormHold()` (3s-hold Easter egg on every Month cell, `ui` egg category, on by default) did this and silently broke every Month cell tap on touch devices, including `onMonthDayTap()`. Touch listeners on anything clickable must stay passive; suppress unwanted follow-up clicks in a capture-phase `click` listener instead |
| Multi-day bars don't inherit cell dimming for free | `.cal-day.other-month` dims a whole cell (and everything rendered inside it) via `opacity`, but `renderMultidayOverlay()`'s bars live in a sibling `.cal-multiday-overlay`, not inside the cells they visually span — so they never picked up that dimming and rendered at full strength on next/prev-month days regardless of source (Google or an ICS sub). Fixed by tagging a bar `.other-month` when every date in its segment is an other-month day, mirrored in CSS (`.cal-multiday-bar.other-month { opacity: .35; }`, same value as the cell rule). Any new overlay-style render path (independent of the cell it visually sits over) needs the same explicit check — it won't inherit dimming from the DOM tree |
| `var(--surface)` is translucent, not opaque | Deliberately so, for cards sitting over the background photo. A modal or popover on it reads as illegible over a busy background or in dark mode; this bit three times (the SMS popover, Event Details, Discover Events). The base `.modal` now reads the opaque `--modal-bg` token, so modals are safe by default; don't give one a `var(--surface)` background, and a new popover outside `.modal` needs `var(--surface-solid)` (or the modal tokens) explicitly. An override must beat `.modal` on specificity (`.modal.x` or `#id .modal`): a bare single-class rule placed before `.modal` loses on source order |
| Settings form that saves on its own button = two Saves | A settings sub-form that writes immediately (Firestore/localStorage) shown beside the modal footer's Save reads as two competing Saves. 🔁 Recurring hit this; its fix is a drill-in screen (`lcOpenRecurForm()`) where `#settingsModal.recur-editing` hides the rest of the panel and swaps the footer to the item's own Cancel/Save. Reuse that pattern for the next multi-field item editor in Settings instead of an always-visible inline form |
| Calendar palette ignores a new color read | While a curated palette is on (`calPalette`, FEATURES.md §Calendar Palettes), every color comes from `memberColor(m)` or `sourceColor(key, own)`. A new render path that reads `m.color`/`sub.color`/`cal.color` directly will show the hand-picked color and clash. New color sources also need a key in `paletteSourceKeys()` |
| SMS popover clipping | `backdrop-filter` on `.card` traps `position: fixed`; append popover to `<body>` then position via `getBoundingClientRect()` |
| Sidebar card compression | `.sidebar > *` must have `flex-shrink: 0` |
| Day stepping by `86400000` ms breaks on DST | A fall-back day is 25 hours, so `new Date(midnight.getTime() + 86400000)` lands at 23:00 the same date: Week view showed Nov 1 twice and dropped Saturday (2026-10-26). Step calendar days with `addDays(date, n)` (`setDate`-based). Dividing a difference by `86400000` is fine if it's `Math.round`ed or UTC-based |
| Photos must be Blobs in IndexedDB | Write photo records through `addBgRecords()` as `{ type, data: Blob }`, never ArrayBuffers. ArrayBuffer records get pulled into memory all at once on every load: 150 photos added ~370 MB at peak (measured 2026-11-12), enough to threaten a phone or the Pi. Old records are migrated once (`fh_bgBlobs`) |
| Errors on the panel go nowhere unless logged | Nobody watches the panel's console. `logError(where, err)` keeps a per-device log (`fh_errorLog`) shown in the control card's status rows, and a load that crashed or froze is reported by the next one (`fh_bootPhase`). Log caught errors that matter there rather than only `console.error` (FEATURES.md §22) |
| `budgetDatesInRange()` returns strings | Returns `YYYY-MM-DD` strings, not Date objects — don't call Date methods on them |
| Budget pill hidden by default | `#budgetTotalCard` starts `display:none`; `renderBudgetCard()` shows it when items exist |
| Budget uses Firestore | Collection `budget` ordered by `createdAt`; `onSnapshot` keeps `budgetItems[]` live |
| Budget privacy toggle is a single gate | `budgetHidden` (per-device `localStorage`, `fh_budgetHidden`) hides $ amounts everywhere by returning `[]` from `budgetEventsForDate(dateKey)` — Month/Week/Day's bill pills and the sidebar card both read through it. Any new render path that shows budget $ amounts by date must call `budgetEventsForDate()` rather than filtering `budgetItems`/`budgetDatesInRange()` directly, or it'll leak past the toggle. It's intentionally per-device like the HA token below — a public wall display can hide amounts while a phone keeps them on |
| Firestore needs Firebase Auth, attached in order | Production rules gate on `request.auth` (Firebase Auth), which is **separate** from the GIS Google token — the app bridges them via `signInWithCredential` in the OAuth callback (needs **Google enabled in Firebase Console → Authentication → Sign-in method**). `setupListeners()` attaches `onSnapshot` then **re-attaches on `firebase.auth().onAuthStateChanged`** — listeners attached before sign-in get `permission-denied` and never recover, so re-attach is what makes shared state load under auth-required rules. Auth failure is surfaced (status pill + control card); don't move listener setup back to a plain load-time attach. |
| Firestore writes silently fail on denied rules | `.add()`/`.update()` reject with `permission-denied` (denied rules, or `request.auth` null because Firebase Auth didn't sign in). Cached reads still render, so it looks like "add does nothing." `addFamilyMember()` surfaces this via `#familyMemberError`; other write paths still swallow it — wrap new writes in try/catch |
| Recipe import needs Netlify functions | `netlify/functions/recipe.js` does the cross-origin fetch + `schema.org/Recipe` JSON-LD parse — browsers can't fetch recipe pages directly. Under plain `python3 -m http.server` the function doesn't exist; `importRecipeFromUrl()` detects that and says to run `netlify dev` (:8888) rather than blaming the recipe. Recipe sites 403 bot User-Agents, so the function sends a browser-like UA |
| NYT JSON-LD is undocumented behavior | NYT Cooking serves the full Recipe JSON-LD unauthenticated even at `isAccessibleForFree: false` — the paywall gates the *render*, not the metadata (probe 2026-07-06). **Not a contract.** If it's gated, the function returns `422 no-recipe` and the UI falls back to "Type It In" — that's the designed failure, don't "fix" it by scraping the rendered page. There is **no API for a user's saved NYT Recipe Box**; only individual recipe URLs work |
| Firestore rejects `undefined` fields | A parsed recipe has sparse optional fields, so recipe writes go through `recipeExtras()` (drops empty/undefined) instead of spreading raw parsed data into `.add()`. Same trap for any new sparse-record write |
| WOTD cache requires definition | Cache entry rejected if `definition` is empty |
| ICS subs = no-OAuth calendars | Subscribe to public/secret `.ics` URLs (`icsSubs`) — events inject into `calEventCache` like Google ones, but carry `readOnly: true`: their `eventId` is the publisher's UID and their `calId` is a subscription, so gate every new **edit** affordance on `isEventEditable(ev)` (as drag and `findCalEvent()` do) or it will PATCH/DELETE a Google URL that cannot exist. Clicks all go through `onCalEventClick(ev)`, which sends ours to the editor and everything read-only to `#eventDetailsModal` (§Event Details). `parseIcs`/`expandRecurrence` handle TZID + RRULE/EXDATE; `fetchIcsSub` falls back to the `netlify/functions/ics.js` proxy (Netlify-only). Local dev can't proxy CORS-restricted feeds |
| ICS recurrence is pragmatic | Supports FREQ DAILY/WEEKLY/MONTHLY/YEARLY + INTERVAL/COUNT/UNTIL/BYDAY/EXDATE only — no BYMONTHDAY/nth-weekday/RDATE/RECURRENCE-ID. Expanded over a ~2 mo back → 14 mo forward window |
| ICS date keys are local | `injectIcsEvent` keys events by `localDateKey()` (not `toISOString()`) — UTC slicing day-shifts evening events in western zones |
| Browser caches JS during dev | Keep DevTools open with "Disable cache" or hard-reload (Cmd+Shift+R) after edits |
| Production CSS/JS can serve stale after a deploy | `netlify.toml` gives `family-hub.html`/`sw.js`/`hub-theme.css`/`family-hub.css`/`family-hub.js` explicit `Cache-Control: no-cache`. The service worker's fetch handler is network-first, but that doesn't bypass the browser's own HTTP cache underneath it: without this header a normal reload (not a hard refresh) can keep serving a stale cached response even though the new deploy is already live on Netlify. A user reporting "the merge/deploy didn't show up" usually means a hard refresh, not a broken deploy; confirm the deploy itself is `ready` on the right commit before assuming otherwise |
| Event Discovery keys | Ticketmaster, OpenWeatherMap, LibraryWeb (per-branch), Red Wings (keyless), CitySpark (keyless), Fairport Festivals (no network at all), Town of Pittsford (keyless page scrape) — set via Netlify env vars in production |
| Fairport Festivals source is curated | `FAIRPORT_SCHEDULE`/`FAIRPORT_WEEKLY` in `netlify/functions/events.js` are the village's published season typed out by hand (2026 today) from the FairportFestivals.com poster; no feed from that site has been confirmed. Re-type it from the new poster each spring; stale years return nothing rather than wrong dates |
| Pittsford calendar is scraped | No feed exists — `fetchPittsford()` pulls the whole event list out of the Drupal `drupal-settings-json` blob on `/calendar`. Board meetings/closures are filtered out; their event tagging is unreliable so don't filter boards by taxonomy colour |
| "Town Events" tab = two sources | Fairport (curated table) and Pittsford (scrape) both emit `source: 'towns'` and share one tab, told apart by `location.address`. `sourceStatus` still tracks them separately so a broken scrape is visible in `sourceStats` |
| Discover Events hides itself when unconfigured | 💡 starts hidden; `probeEventsBackend()` asks the function (`?status=1`) whether `OWM_KEY`/`TICKETMASTER_KEY` are set and shows 💡 (and the Live Events tab) only if so, plus a per-device Settings toggle. A new keyed source should report itself in that probe the same way rather than shipping an always-empty tab |
| Event Discovery backend | Runs on `/.netlify/functions/events`; geocoding via OWM; exponential backoff retry (2x, 1s→4s) for API failures |
| Events function must answer inside Netlify's 30s | All sources are awaited together, so one hung upstream 504s the whole response (Overpass did, 2026-10-20, and the modal showed "No live events"). The module shadows `fetch` with an 8s `AbortSignal.timeout`, each source is capped at 12s by `withTimeout()` and marked unavailable in `sourceStatus`, geocoding at 6s, and weather enrichment gets a 5s budget with one forecast per ~1° cell. Keep new sources inside the same `capped(...)` list. Overpass never answered Netlify again, so Things to Do moved to the browser (`loadThingsToDo()`); `warnings` now carries each failed source's reason |
| CitySpark sort parameter | MUST use `sort:'Time'` (soonest-first); `'Date'` returns the tail of future events and fails the 30-day filter |
| HTTPS page can't call a LAN box | The hub is served over HTTPS, so `http://homeassistant.local:8123` is blocked three ways over (mixed content, our `connect-src`, HA's CORS). Home Assistant is reached at its Tailscale `https://….ts.net` name, which the blanket `https:` in the CSP already allows. `http://localhost:8123` is in `connect-src` for `tests/ha-mock.js` only |
| HA CORS failure looks like a dead host | A CORS rejection reaches JS as a bare `TypeError`, identical to "the host is down". `haFetch()`'s `unreachable` message names both causes deliberately; don't "simplify" it to one |
| HA token is per-device on purpose | `fh_haToken` is excluded from the Firestore settings sync (`haConfig` is synced, the token isn't). A long-lived HA token controls every entity its user can see, so per-device means individually revocable. Don't add it to the sync list |
| HA service calls aren't instant | Z-Wave/Zigbee devices take seconds to report a new state. `haRecheckEntity()` re-reads at 1s and 4s before handing back to the 120s poll — a single immediate re-read reports working devices as failures |
| Mobile SpeechRecognition is best-effort | The Assistant mic (`initAssistantVoice()`) feature-detects `SpeechRecognition`/`webkitSpeechRecognition` and hides the button when absent — reliable on Android Chrome, but iOS Safari's implementation (also used by every browser on iOS, since they're all WebKit under the hood) has a history of interim-results and permission-API quirks Apple doesn't fully document. `showMicDeniedHelp()` branches on `isIOSDevice()` for the right permission path (iOS has no in-page address-bar 🔒 icon — it's Settings → Safari → Microphone) but the deeper behavioral quirks are unverified on a real device; treat iOS voice input as needing real-device follow-up, not a closed loop |
| Chromium's SpeechRecognition can't reach its service | Open-source Chromium builds (Raspberry Pi OS ships one) expose `webkitSpeechRecognition` but fail every session with a `'network'` error, because they lack Google's speech API keys. That error flips the device to `assistantVoiceEngine = 'gemini'` (`fh_voiceEngine`): record with `MediaRecorder`, transcribe with Gemini, auto-send. Feature detection alone can't catch this, since the API is present |
| Wall panel sound is Pi-side config | No sound on the panel is almost never hub code. The fixes live on the Pi (`family-hub-setup.md` step 10c): HDMI as the default output (the USB mic grabs it), an inaudible keep-awake hum because the monitor mutes on silence, `--autoplay-policy`/`--enable-speech-dispatcher` on the launch line, and Piper as speech-dispatcher's only module (the Assistant speaks with Gemini; Piper is the fallback voice). Restart it with `pkill -x speech-dispatch`; `pkill -f speech-dispatcher` matches Chromium's flag and kills the hub. Pond Chimes is still silent there (SCREENSAVER_BACKLOG.md) |

## Adding a Feature — Checklist

1. **State:** `let featureState = lsGet('fh_featureName', default)` near similar features
2. **CSS:** `/* ── Feature Name ── */` section in `family-hub.css`; use existing CSS vars; theme variants if needed
3. **HTML:** card in `.sidebar` or modal in `<body>`
4. **JS:** `// ── Feature Name ──` section in `family-hub.js`
5. **Widget?** add to `WIDGET_DEFAULTS`, `WIDGET_PLACEMENT_DEFAULTS`, `WIDGET_ORDER`. Most widgets have no mobile surface at all (Settings-only, like Budget/Chores/Word of the Day); if this one genuinely needs day-to-day phone use, add it to `MOBILE_SHEET_SECTIONS` and give it a tab in the Lists sheet markup (§20) instead of inventing new mobile chrome
6. **Settings?** add a `modal-tab` + `settings-panel`; wire into `openSettings()` (populate) and `saveSettings()` (persist). In `saveSettings()`, persist + `closeSettings()` **before** any re-render that could throw.
7. **Init:** call setup from `window.addEventListener('load', ...)` as its own `bootStep('name', fn)`, so a throw is logged and skipped instead of stopping every step after it (FEATURES.md §22)
8. **Docs:** update `FEATURES.md` (function/state/anchor/key) + `CLAUDE.md` if architecture changed

## How to Find Things Quickly

```bash
grep -n "function functionName" family-hub.js   # JS function
grep -n "id=\"elementId\""       family-hub.html # HTML element
grep -n "\.class-name"           family-hub.css  # CSS class
grep -n "fh_keyName"             family-hub.js   # localStorage key
grep -n "^// ──"                 family-hub.js   # JS section boundary
grep -n "^/\* ──"                family-hub.css  # CSS section boundary
```

When editing, use `Read` with `offset` + `limit` to read only the relevant section — these files are large.

## Verification — prefer DOM/JS inspection over screenshots

When checking that a change worked in the browser, **default to `javascript_tool` (read `el.style.display`, `innerHTML`, computed values, state vars) rather than screenshots.** Screenshots cost ~1,000–1,500 tokens each; a DOM/state read costs a fraction of that. Reserve screenshots for genuinely *visual* questions (does this look right / is it aligned) — not for "did it toggle / render / update."
