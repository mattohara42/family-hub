# Printing Press API Analysis & Backend Integration Improvement

**Branch:** `feat/printing-press-api-analysis`  
**Depth:** Standard (focused API research and integration enhancement)

---

## Problem Frame

The Family Hub event discovery backend currently uses hardcoded integrations with Ticketmaster and Eventbrite APIs. While functional, the integration is:
- Limited to a small subset of available endpoints
- Lacks comprehensive documentation of API capabilities
- Could benefit from deeper understanding of available data and filtering options

**Core Insight:** Using Printing Press to discover and map the full API surfaces can reveal untapped capabilities, improve documentation, and provide a foundation for richer event discovery features.

- ✅ Improved backend code clarity with specification-driven documentation
- ✅ Exploratory analysis for estatesales.net scraping approaches
- ✅ Foundation for potential CLI generation or enhanced integrations

## Key Technical Decisions

### 1. Printing Press for API Discovery

**Decision:** Use Printing Press to discover API surfaces via `crowd-sniff` (SDK/community analysis) and `probe-reachability` (transport verification).

**Why:** Printing Press provides:
- Automated endpoint discovery from published SDKs
- Proper auth detection and environment variable inference
- Transport requirements analysis (browser capture, clearance cookies, etc.)
- Machine-readable spec output compatible with CLI generation

**Limitation:** Printing Press is designed for APIs, not web scraping. Exploratory phase will determine if it's suitable for estatesales.net; if not, defer scraper analysis to follow-up work.

### 2. API-First Documentation Approach

**Decision:** Use generated specs as the source of truth for API understanding, rather than reverse-engineering from SDK code.

**Why:** Specs are machine-readable, easier to keep in sync, and can be version-controlled alongside the backend code for future reference.

### 3. Exploratory, Not Prescriptive

**Decision:** For estatesales.net, run exploratory analysis with Printing Press; do not commit to scraper CLI implementation until findings are complete.

**Why:** Printing Press may not be suitable for web scraping discovery. Premature implementation commitment risks wasted effort; exploration first allows informed decision-making.

   - Discount and promotion endpoints
   - Order and attendee management endpoints

- Reference the Eventbrite spec YAML at `/tmp/eventbrite-spec.yaml` (or regenerate as needed)
- Follow existing backend code structure for API integration patterns
- Document findings in a new `docs/API_RESEARCH.md` file

**Test Scenarios:**
- Spec covers 61 unique endpoints with distinct resource types ✓
- Current implementation uses ~5 endpoints (estimated from code review) ✓
- Identified at least 3 search/filtering endpoints not currently used ✓
- Auth requirements correctly understood (Bearer token, env var EVENTBRITE_API_TOKEN) ✓

### U2. Research Ticketmaster Full API Surface

**Goal:** Determine why Printing Press discovered only 2 endpoints from Ticketmaster and map the actual full API surface.

**Requirements:** Complete understanding of Ticketmaster Discovery API capabilities

**Dependencies:** U1 (for context on API discovery approach)

**Files:**
- `netlify/functions/events.js` (read existing integration)
- `docs/API_RESEARCH.md` (append findings)

**Approach:**

1. Investigate why `crowd-sniff` returned minimal endpoints for Ticketmaster:
   - Check if Ticketmaster publishes an official SDK or if community SDKs are thin
   - Review Ticketmaster developer portal documentation
   - Search for open-source integrations with richer endpoint coverage

2. Manually map the Ticketmaster Discovery API v2 surface:
   - Read official API docs at https://developer.ticketmaster.com/
   - Document all available endpoints (events, venues, attractions, classifications, etc.)
   - Note auth method (API key in query param) and rate limits

3. Compare discovered endpoints to current implementation:
   - Current code uses: `/events.json` with filters (latlong, radius, size, sort)
   - Map any additional endpoints that could enhance functionality

4. Identify expansion opportunities:
   - Venue details endpoint
   - Attraction/artist details
   - Classification browsing
   - Advanced filtering not currently used

**Patterns to Follow:**
- Follow existing backend integration patterns (error handling, retry logic)
- Document findings in `docs/API_RESEARCH.md`
- Preserve current hardcoded constants (`TM_API_BASE`, etc.)

**Test Scenarios:**
- Official API documentation is accessible and current ✓
- At least 10 distinct endpoints identified in Ticketmaster Discovery API ✓
- Current implementation covers only a subset of available functionality ✓
- Auth method (API key) and rate limits are documented ✓
- Expansion opportunities are clearly identified with endpoint paths ✓

**Verification:**
- `docs/API_RESEARCH.md` includes Ticketmaster endpoint catalog
- Explanation for why `crowd-sniff` found minimal endpoints
- At least 5 expansion opportunities documented
- Comparison matrix: current vs. full API capability
